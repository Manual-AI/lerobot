# GR00T Policy

GR00T is an NVIDIA foundation model family for generalized humanoid robot reasoning and skills. It is a cross-embodiment policy that accepts multimodal input, including language, images, and proprioception, to perform manipulation tasks in diverse environments.

LeRobot integrates GR00T N1.7 through the `groot` policy type.

> [!WARNING]
> **Breaking change:** GR00T N1.5 support was removed from LeRobot, and current releases support GR00T N1.7 only. N1.5 checkpoints and configs are rejected with a migration note. To keep using an N1.5 checkpoint, pin the last release that supports it: `pip install 'lerobot==0.5.1'`. To use the current release, migrate to GR00T N1.7 (base model [`nvidia/GR00T-N1.7-3B`](https://huggingface.co/nvidia/GR00T-N1.7-3B)).

## Model Overview

GR00T N1.7 uses a Cosmos-Reason2/Qwen3-VL backbone and provides checkpoints for SimplerEnv, DROID, and LIBERO.

Developers and researchers can post-train GR00T with their own real or synthetic data to adapt it for specific humanoid robots or tasks.

GR00T uses pre-trained vision and language encoders with a flow matching action transformer to model a chunk of actions conditioned on vision, language, and proprioception.

  src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/lerobot/lerobot-groot-paper1%20(1).png"

Its strong performance comes from being trained on an expansive and diverse humanoid dataset, which includes:

- Real captured data from robots.
- Synthetic data generated using NVIDIA Isaac GR00T Blueprint.
- Internet-scale video data.

This approach allows the model to be highly adaptable through post-training for specific embodiments, tasks, and environments.

## Installation Requirements

GR00T is intended for NVIDIA GPU-accelerated systems. Install LeRobot with the GR00T extra:

```bash
pip install "lerobot[groot]"
```

For a source checkout:

```bash
pip install -e ".[groot]"
```

## Usage

To use GR00T N1.7:

```bash
--policy.type=groot
```

## Training

### Training Command Example

Here's a complete training command for finetuning the base GR00T model on your own dataset:

This command is using the `new_embodiment` flag, which is used for the SO-101 robot, [read more about how GR00T handles different embodiments.](https://github.com/NVIDIA/Isaac-GR00T/blob/main/getting_started/policy.md#--embodiment-tag).

```bash
# install extra deps for training
pip install "lerobot[training]"

hf auth login
wandb login

export DATASET_NAME=your_data_set
export HF_USER=your_hf_username
export DATASET=$HF_USER/$DATASET_NAME
export REPO_ID="${DATASET}_GR00T17" #this is the model that will be uploaded to huggingface
export OUTPUT_DIR=outputs/train/$REPO_ID

lerobot-train \
  --dataset.repo_id=$DATASET \
  --dataset.image_transforms.enable=true \
  --policy.type=groot \
  --policy.device=cuda \
  --policy.base_model_path=nvidia/GR00T-N1.7-3B \
  --policy.embodiment_tag=new_embodiment \
  --policy.chunk_size=16 \
  --policy.n_action_steps=16 \
  --policy.use_relative_actions=true \
  --policy.relative_exclude_joints='["gripper"]' \
  --policy.use_bf16=true \
  --policy.push_to_hub=true \
  --policy.repo_id=$REPO_ID \
  --seed=42 \
  --batch_size=64 \
  --steps=20000 \
  --save_checkpoint=true \
  --save_freq=5000 \
  --use_policy_training_preset=true \
  --env_eval_freq=0 \
  --eval_steps=0 \
  --log_freq=10 \
  --output_dir=$OUTPUT_DIR \
  --job_name=$DATASET \
  --wandb.enable=true \
  --wandb.disable_artifact=true

```

### Evaluate in your hardware setup

Once you have trained your model using your parameters you can run inference in your downstream task. Follow the instructions in [Policy Deployment (lerobot-rollout)](./inference). For example:

```bash
# install extra deps for roullout and real hardware
pip install "lerobot[feetech,viz]"

export MODEL_ID=your_trained_model_on_huggingface

# make sure that camera index matches your setup!
# find index using `uv run lerobot-find-cameras opencv`
WRIST_CAM='wrist: {type: opencv, index_or_path: 2, width: 640, height: 480, fps: 30, fourcc: "MJPG"}'
FRONT_CAM='front: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30, fourcc: "MJPG"}'
export ROBOT_CAMERAS="{ $WRIST_CAM, $FRONT_CAM }"
export ROBOT_ID=follower_robot
export ROBOT_PORT=/dev/ttyACM0

# Set --inference.rtc.enabled=False if RTC causes inference instability
uv run lerobot-rollout \
  --strategy.type=base \
  --policy.path=$MODEL_ID \
  --policy.base_model_path=nvidia/GR00T-N1.7-3B \
  --policy.n_action_steps=8 \
  --robot.type=so101_follower \
  --robot.port=$ROBOT_PORT \
  --robot.id=$ROBOT_ID \
  --robot.cameras="$ROBOT_CAMERAS" \
  --task="place the vial in the rack" \
  --duration=60 \
  --device=cuda \
  --display_data=true \
  --inference.type=rtc \
  --inference.rtc.enabled=True \
  --inference.rtc.execution_horizon=8 \
  --inference.queue_threshold=0
```

> [!NOTE]
> Value of `inference.queue_threshold` should not exceed 5 to ensure stable inference.

#### RTC with relative actions

Checkpoints fine-tuned with `--policy.use_relative_actions=true` predict actions as deltas
against the observation they were predicted from, normalized with one statistics row per chunk
step. RTC therefore cannot reuse the previous chunk's model-space output as the overlap prefix:
those rows are anchored to the previous observation and to the previous chunk's step indices.
Instead it takes the unexecuted tail in absolute coordinates, re-expresses it against the current
observation (an SE(3) delta for end-effector groups, an elementwise offset for the rest), and
normalizes each row with the statistics row of its new chunk step. No extra flags are needed —
this happens automatically for relative-action checkpoints under `--inference.type=rtc` and on a
policy server running RTC. With a non-invertible `action_decode_transform` (such as the LIBERO
gripper transform) the absolute tail cannot be re-encoded, so chunks are predicted without
overlap guidance and a warning is logged once.

## Online fixed-factor action targets

`dataset.online_action_resampling` opts into action-only time stretching for a single-observation,
relative-EEF GR00T recipe with absolute fingers and `action_delta_offset=0`. The default `null`
keeps the existing dataset path. Install the `scipy-dep` extra for SO(3) interpolation.
The typed `OnlineActionResamplingConfig` lives in `lerobot.configs.online_action_resampling`
and is also exported by `lerobot.datasets.online_action_resampling`.

The config requires an immutable dataset `source_revision`, positive `source_fps`, `output_fps`
and `stretch_factor` (identity default `1.0`), exact per-group `group_delays` in source frames,
and explicit `source_contract` provenance. The contract records
`reservoir="state_plus_recorded_action_tail_v1"`,
`recorded_action_semantics="per_group_delay_compensated"`,
`state_semantics="pre_delay_same_frame"`, `rotation_encoding="row_rot6d"`,
`time_stretch_applied=false`, `idm_applied=false`, `calibration_sha256`,
`pre_delay_source_revision`, and `delay_source_revision`. Additional provenance fields are
included in the canonical identity. Supply verified lineage; processed stretches or missing
pre-delay provenance are not valid inputs.

Each loaded episode must satisfy exact state/action overlap at every group's recorded delay.
The numeric reservoir combines the unshifted state channels and the retained action tail;
no missing samples are reconstructed. Pose groups use names such as `right_ee_pose`, resolving
`right_ee_pos_{x,y,z}.pos` and `right_ee_rot_{0..5}.pos` from feature metadata. Scalar groups use
exact action feature names. Every action channel must be covered. The target builder resolves
state channels by name; the GR00T training factory additionally requires the state/action
prefix alignment and canonical XYZ/row-rot6d pose order used by its relative-action processor.

For anchor `i`, output step `k`, delay `d` source frames and stretch `s`, the source query is
`i + (k * source_fps / output_fps + d) / s`. Thus delay remains fixed in output robot time.
Translation and fingers interpolate linearly, row-convention rot6d interpolates on SO(3), and
integer queries preserve stored values exactly. Unsupported brackets clamp to the recorded
endpoint and mark the whole action step as padding. Statistics exclude an entire chunk if
any step is padded, matching the existing identity behavior.

Images, current state and anchor sampling are unchanged. Scalar and batched reads, selected
episodes, train/eval splits and both GR00T statistics paths use the same numeric builder.
Streaming, feature renaming, nondefault storage and other policy combinations are rejected.
`build_absolute_action_targets(...)` is the video-free array API;
`dataset.get_online_action_sample(index, chunk_size=None)` returns `(action, state, is_pad)`
without decoding images. Config `identity()` and `fingerprint()` include source provenance,
selected episodes, timing, interpolation and statistics support rules for callers' cache and
resume checks. Raw online GR00T initialization always computes target statistics from the selected
training episodes, including absolute fingers, even if a checkpoint or caller supplies statistics.
At `stretch_factor=1.0`, raw targets and padding exactly match the recorded compensated actions;
final finger normalization can still differ from the disabled path, whose metadata statistics may
cover a different episode population or include samples excluded by whole-chunk support.
Saved processors persist a statistics identity covering the target fingerprint, native statistics horizon, valid action horizon and
relative group geometry. Training accepts serialized processors only when that identity
matches the dataset, including whether online resampling is enabled; for missing or mismatched identities, initialize from a raw N1.7 checkpoint to recompute.
Inference without dataset metadata can load those processors directly. Train/eval metadata carries
each resolved population while the saved dataset config retains the overall episode selection.
